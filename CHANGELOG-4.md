## 2026-10-18 — the props schedule never fired, and the pull moved
- **The report (Danny, 9:53 AM CT):** "Still has not loaded - Jacksonville vs Houston already kicked off."
- **Not a code fault.** `gh workflow list` showed **NFL props / active**, and a manual `workflow_dispatch` in plan mode came back green on every step - checkout, the shape tests, the pull, the page boot, the commit. The pipeline was sound. **GitHub had simply never run the cron**, not once, in 14 hours. `20 13-23 * * 0,1,4` includes Sunday, and 13:20 and 14:20 UTC had both passed.
- **Why:** scheduled runs on this repo are dropped and delayed badly. `refresh.yml` should have run six overnight slots (00:05-05:05 UTC) and ran three - 00:41, 04:17, 09:27 - the last **4h22m** late. A brand-new schedule competing for the same queue lost every time. This was visible in Saturday's sync (the refresh firing every 2-3 hours instead of hourly) and was left as a footnote instead of treated as a constraint; props were then built on exactly the mechanism that was already known to be unreliable.
- **Fixed (ruling 1 of 2026-10-18):** the pull moved into `refresh.yml` as a `continue-on-error` step after the lines commit, so a props failure can never cost a lines refresh. `props.yml` deleted.
- **`due()` rewritten to tolerate delay.** The old version wanted a run inside a +/-30 minute window, plus a morning sweep that fired only when `now.hour == 14` - so today's 15:00 run missed the sweep and the late games got nothing. Now: a game nobody has priced is pulled the first time any run sees it, then marks are claimed nearest-kickoff-first, each at most once, and a mark whose moment has passed is still taken up to 45 minutes late. Better a number 40 minutes before kickoff than no number at all. Ten assertions cover it, including a game whose 2-hour run was dropped still getting a late price.
- **One manual pull with Danny's go** (~48 credits): 7 noon games, 421 props, `e1c3864`. JAX/HOU was already gone and is not recoverable.
- **Two bugs found by using the real page, again.** (1) Every row read **"—"** until a number was typed - 421 dashes on open - because the Chance cell priced only the typed number, while `DESIGN.md` said a blank field prices the book's line. It now prices the book's line by default, and falls back to it when the field is cleared. (2) `props.js` is 81 KB of generated data and the file-size guard fails anything over 24.8 KB, so the next code push would have gone red on a file nobody edits by hand; it joins `ratings.js` in `MACHINE_WRITTEN`.
- **Cache tag `?v=20261018a`, bumped in the same commit as the page change** - the lesson from last night, applied.

## 2026-10-18, afternoon — prop type filters, and the card redrawn from Danny's sketch
- **The ask:** "I need filters for type of prop on the NFL props screen." Three options were drawn on real data (pick one / pick any / four groups) rather than described; Danny then asked what it would take to add **defensive props, fumbles, special teams, field goals, PATs, and the QB and skill-position combos**, which changed the shape of the answer.
- **What that research found.** The-odds-api carries combos (`player_pass_rush_yds`, `player_rush_reception_yds`, `player_pass_rush_reception_yds`), defence (`player_sacks`, `player_solo_tackles`, `player_tackles_assists`, `player_defensive_interceptions`) and kicking (`player_field_goals`, `player_pats`, `player_kicking_points`). **Fumbles are not offered at all.** Credits are not the blocker - 19,344 of 20,000 were left on the 18th, and all ten markets live would cost about 2,000 a month. The blockers are (a) **no fitted shape**, which is what lets Danny type a number off the book's line, and a 2025 re-pull to fit one runs ~2,800 credits per market, so ten is more than a month's plan and three is affordable; and (b) **no correction study** of the kind `DECISIONS.md` 8 did for the six current markets. Grading is the easy part: the nflverse file `props_grade.py` already reads carries `def_sacks`, `def_interceptions`, `def_tackles_solo`, `fg_made`, `pat_made` and the fumble columns.
- **So the filter was built two-level** (ruling 3), because a flat row of six chips becomes sixteen the moment combos and defence land. Adding a group later is one line in `PROP_GROUPS`.
- **The header bug Danny caught, by reading his own screen.** He asked what the columns meant - "Prop says DK 233.5, is that passing + rushing?" - and the honest answer was that the headings were lying to him. `.mk` was hidden under 760px on the `<td>` only, never the `<th>`, so the Prop column vanished and every heading shifted one column left. It had been live since the tab shipped on 10/17 and no test caught it, because the tests check what the page computes, not whether its headings line up with its cells.
- **His sketch beat both of the fixes offered for it** (ruling 4): make the prop type a heading inside the card and the column the bug lived in stops existing. 59 rows on the Bears/Falcons card carried 59 repeated prop labels; now three headings carry them. Second time an Excel sketch of Danny's has set a layout.
- **Anytime TD opens shut** (ruling 5) - 185 of today's 421 props, none with a number to type. The same card went from 59 rows to 35.
- **Twenty new checks in `ci/smoke_props.js`**, including the two cases that matter for a filter nobody will re-read later: a search hit must not hide inside a closed heading, and a market the page has never been taught must still reach the board.
